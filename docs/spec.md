# spec

hanoba の製品仕様・画面挙動（非ビジュアル）。見た目は `DESIGN.md`、コード構成・データ契約は `docs/architecture.md` を参照。
本書は元 DESIGN.md の §1 原則・§4 主要画面・§7 Non-goals・§8 Open を集約したもの（session765 の3層分割・内容は逐語移設）。

> 植物写真の SNS。1投稿 ＝ 正方形写真1〜4枚 ＋ ひとこと（必須）。**「育てて、見せる。」**
> **mypace（Nostr）のスキン**であり、自前のバックエンドを持たない。Instagram より早く・簡単に、文章を添えて植物を見せる場。長期目標は架空の植物好き都市ハノーバ(Hanoba)をみんなで作ること。

## 1. 原則（規律）

1. **正方形固定** — 投稿画像は正方形に矯正。クロップはドラッグで位置決め。1投稿に1〜4枚まで入れられる。
2. **一言必須** — 写真だけの投稿を許さない。`content` 空は弾く。これが心臓部。
3. **動画非対応** — 身バレ（背景の映り込み・環境音・反射・複数フレーム）回避。静止画のみ。
4. **植物だけ** — テーマは固いが、その枠内は何でも OK（自慢・実験メモ）。

## 4. 主要画面

- **投稿**: 撮影/選択（最大4枚）→ 写真ごとに正方形クロップ（ドラッグ）→ 植物写真向け補正（選択式）→ 一言（必須）→ 投稿
  - **撮影とアルバムはボタンを分ける（#29）**。単一 input に `capture="environment"` を付けるとスマホでカメラ直起動が優先されアルバムから選べなくなるため、`capture` 付き input（撮影）と `capture` 無し input（アルバム）を別ボタンで持つ。
  - **必須・不足理由の a11y（#151）**: 「一言（必須）」は視覚ラベルに「（必須）」と書かず（#149）プログラム属性で支援技術に伝える＝一言 `<textarea>` に `aria-required="true"`。投稿できない理由「あと ◯◯ を入れると投稿できます」は `role="status"`＋`aria-live="polite"` で状態変化を能動読み上げ。送信ボタンは不足があるときだけ `aria-describedby` でその不足理由を指し（充足したら属性ごと外す＝dangling 参照を作らない）、disabled の理由をボタンから辿れるようにする。
- **フィード（読めるフィード・#34/#50）**: hanoba の売り＝**本文を切らず読め、1クリックも要らない**（vs Instagram）。縦並びカード（PostCard）。sm 以上＝写真左／本文中／タグ右の縦列、モバイル＝写真上／本文／タグ下。**本文テキストからは #タグ を除き**（stripHashtags）タグは右列に出す。**デスクトップはカード高さを写真の正方形（sm:h-56）に固定**し、本文・タグをその中に収める（はみ出しは clip）＝写真の下に隙間を作らない。本文かタグが clip された時だけ**「続きを読む」**（フェードは使わない）でカード全体を展開し全文＋全タグを表示。**全文が読めているカード（展開済み、または clip されていない短文）**は本文末尾に「花を添える」「コメント」の控えめな導線を出し、押すと既存の PostDetail モーダルを開いて該当操作へ寄せる（長文が clip された展開前だけ出さない＝未読のまま反応を強く促さない）。自分が花を添えている投稿は、カードの導線も塗り花＋「花を添えた」で表示する。タグが多くても**1列のまま下を見切る**（2列に折り返さない・#54）。**カードの非インタラクティブ領域はどこを押しても拡大**（PostDetail モーダル・写真/リンク/タグ/「続きを読む」/反応導線は個別動作を維持＝stopPropagation・写真ボタンはキーボード/SR の主導線として残す・#101）。**複数写真カードは写真領域内だけで現在写真を切り替えられる**（#522）。タッチ端末は写真領域の左右スワイプ、マウス環境は写真領域 hover/focus 時だけ出る左右矢印で前後移動する。単一写真カードには矢印を出さない。切替 index・スワイプ判定・スワイプ中 blur は投稿詳細と同じ `src/lib/feed/carousel.ts` の純関数を使い、`prefers-reduced-motion` 時はスワイプ中 blur を無効にする。**カードで2枚目以降を見てカードを開くと、PostDetail も同じ写真から始まる**（URL deep-link はカード状態を持たないため従来どおり1枚目開始）。**読み込み中はカード形のガラス pulse スケルトン**（FeedSkeleton・素っ気ない「読み込み中…」を置き換え・#99）。カード（写真）の角丸は控えめ（rounded-xl・#100）。**大画面（lg）はカード幅を広げ（max-w-5xl）、余白は主に写真を大きく**（写真 224→288px・#56）。植物タグで絞る。
- **投稿頻度の高い人をフィードで「減らす」（#138）**: 人ごとに **1/2・1/5・1/10** の間引き度合いを設定でき、その人の投稿をフィードで決定的に間引いて表示する（ミュートの手前の柔らかい手段）。判定は `hash(post.id) % level === 0`（FNV-1a・id 由来）＝**deterministic**でリロードしても残る投稿は同じ・相対順序は保つ。状態（pubkey→level）は集約 localStorage（単一キー `hanoba` の `dilution` フィールド・#558）を `src/lib/feed/dilution.ts` が `appStorage` 経由で読み書きする（純関数 `diluteFeed(posts, map)`）。適用は取得済みリスト→表示の間（`PostGrid`＝フィード/discover 共通）に1段挟む。**`/me`（自分の投稿）には掛けない**＝自分を減らさない。UI は投稿詳細モーダルの著者ヘッダ下に置く `DilutionControl`。**既定は畳む**（控えめな入口・未設定は中立文言「{名前}さんの表示を調整」／設定中は「1/N に減らし中」）＝既定が「なし」なのに常駐すると「減らすのが基本」と誤解させるため。開いたときだけ **なし・1/2・1/5・1/10 の4点にスナップするスライダ**（native range＋`aria-valuetext`・中間の無意味値を出さない）が出る。見出しは**人に明示**「{名前}さんの投稿をフィードで減らす」（"薄める"は植物アプリで"植物を薄める"とも読めるため廃止）。設定すると即フィードに反映（同タブはカスタムイベント、別タブは storage で同期）。
- **トップ と みんなの植物 の住み分け（#52）**: **トップ**＝`t:hanoba` のみ（葉の場＝ローカル）。**みんなの植物（discover）既定表示**＝`#plantstr`（Nostr 全体の植物界隈）∪ `t:hanoba` の**マージ**（id 重複除去・時系列）。hanoba は全投稿に `t:plantstr` を自動付与する（#383・reciprocity＝`architecture.md` の §6。discover が `#plantstr` を読むだけの非対称を解消し、自分の投稿を Nostr 全体の植物界隈にも露出させる）。`t:hanoba` 経由でも自分の投稿が「みんな」に出る（「投稿したのに見えない」混乱の解消）。個別検索（`?q=`）は `architecture.md` の §6 の横断検索のみ。各画面に1行の住み分け説明を置く。
- **もっと見る（#554）**: トップ・みんなの植物・あなたの植物の3フィードは、初期表示ぶんの先を**「もっと見る」ボタン**で追加読み込みできる（時間窓ページング＝`architecture.md` の §6・過去へ遡って追記）。**無限スクロールにはしない**（静けさ優先・押した時だけ増える）。これ以上古い投稿が無ければボタンは消える。見た目は既存の再取得ボタン準拠（新トークンを増やさない）。
- **市勢調査（UI ラベル。旧称「人気ランキング」・#162・#525・`/ranking`）**: 植物**品種**の人気を音楽チャート風に出す。**バックエンドレス**（`architecture.md` の §6・集計サーバを持たない）で、取得済みの **`t:hanoba` 投稿だけ**（`fetchRankingPosts`・既定 limit 500・画像ありのみ＝フィードと同母集団）を**クライアントで数える**「読むたびに数える」方式。母集団を `t:hanoba` 限定にするのは、**自分の投稿が見えてチャートを動かす＝投稿の動機**にするため（discover の横断集約は混ぜない）。集計と差分は純粋ロジック `src/lib/feed/ranking.ts`（relay も `Date.now()` も持たず `now` を引数で受ける＝テスト可能）に集約し、島 `RankingBoard` は取得・`now=Math.floor(Date.now()/1000)` の供給・描画だけを担う。
  - **集計単位＝品種**: 各投稿の `hashtags` を **`buildFuda`（§4 札・#182/#23）** にかけて品種（`{key,name(和名),sci(学名)}`）に畳み、品種ごとに投稿数を数える（`tallyVarieties`）。属/品種の畳み込み・alias の canonical 寄せ・**同一投稿内の重複 dedupe** は `buildFuda` に一本化する（同じ品種の別名を1投稿で複数付けても1票）。同一品種が複数投稿に出れば投稿ごとに加算。票数降順・同数は**初出順**で安定。
  - **週次バケット**: `isoWeekKey`（ISO 8601・**月曜始まり・UTC**・年/週番号は木曜基準。例 `2026-W25`）で投稿を週に振り分ける（`bucketByWeek`・古い→新しい）。`now` の指す週が「現在の週」。
  - **先週比（`rankWithDeltas`）**: 「直前の週」＝現在週より前で**データのある直近の過去週**（カレンダー連続でなくてよい）。**NEW**＝現在週より前のどの週にも一度も載っていない。**RE**＝過去に載ったが直前週には不在で今週復帰。**↑N/↓N/—（same）**＝直前週との順位差。**直前の過去週が無い（初週）なら全行 NEW**（偽の矢印を出さない）。NEW/RE は**取得済みの直近ウィンドウ内**（`fetchRankingPosts` 上限＝現状およそ直近 500 投稿）での判定で、全履歴に対する絶対判定ではない。**初週バナー**（「先週比は来週から」）は全行 NEW を代理にせず**データのある週数が実質 1 週以下**のときだけ出す（後発の週がたまたま新規品種ばかりでも誤って初週と出さない）。
  - **途中経過（変動）チャート（#162・uPlot）**: 順位の**表**の下に、上位 5 品種（`CHART_TOP=5`）の週次票数の推移を **1枚の折れ線チャート**で重ねる（x＝ISO 週・古い→新しい、y＝その週の票数＝整数、1品種1線・凡例＝和名）。維持者方針「変動はグラフなら uPlot のような軽量 lib を使う」に従い、**軽量・MIT・依存ゼロ・canvas の uPlot** を採用（純データは `rankRunData(posts, catalog, keys)`＝**最古〜最新の投稿週までをカレンダー上で連続させた**週列に整列した票数マトリクス・投稿の無い空週も 0 埋めで補完して線を連続させ x 軸を等間隔に保つ・連続軸は `isoWeekMondayUtc` の月曜タイムスタンプを 7 日刻みで列挙して作る＝年またぎの週番号算術を避ける・テスト可能）。uPlot は `window`/canvas に触れるので **クライアント専用＝マウント後に動的 import**（SSG ビルド中に走らせない）し、`RankRunChart` 自体も `React.lazy` で**遅延ロード**（チャートを出すときだけ uplot チャンクを取得・初期描画を軽く）。暗いシック地に合わせ軸/グリッド/ラベルはパレットの ink、**線色は global.css のトークン値だけ**（緑/オレンジ/黄/明るい葉/ink の 5 色＝`CHART_TOP=5` と一致・新色を足さない `DESIGN.md` の §5.1・重い塗りはしない）。canvas は装飾なので `aria-hidden`＝**意味は上の表（順位・品種・学名・件数・先週比）が正本**（行の `aria-label` は和名に学名も添える）。図には説明的 `aria-label` を付ける。reduced-motion: uPlot は既定で非アニメーション。**週が2つ未満なら退化グラフを描かず**「推移グラフは週が2つ以上たまると表示されます。」の注記に差し替える（潰れた線を見せない・RankingBoard 側でも同条件で gate）。
  - **まばらデータの作法（launch 直後の少投稿で壊れて見せない）**: 読み込み中は静かに「読み込み中…」。投稿/品種ゼロは正直に「まだランキングを出すほどの投稿が集まっていません。」＋投稿 CTA。**単週のみなら全 NEW**＋「先週比は来週から」の注記（偽の ↑↓ を出さない）。件数は小さくても正直に出す。
  - **色**: 差分バッジはパレット内（NEW/RE/↑＝緑系、↓/—＝控えめ ink）。新色は足さない（`DESIGN.md` の §5.1）。
  - **開発専用プレビュー（`?demo`）**: `import.meta.env.DEV` **かつ** URL に `?demo` のときだけ、合成 fixture（`src/lib/feed/ranking.demo.ts`・複数週/差分/途中経過チャートの複数系列を作り込んだダミー）を使う＝`npm run dev` でリレーに**何も publish せず**リッチ状態を確認できる。**本番ビルドでは `import.meta.env.DEV=false` でこの分岐ごとデッドコード化**（fixture も banner 文字列もバンドルに残らず、本番ページは捏造データを一切出さない）。
  - **言語別ランキングは #147（i18n）待ちで deferred**: 当面は日本語（和名＋学名）で描画する。
- **著者ヘッダ（#35・#103・#531）**: 投稿カード・投稿詳細・コメント・公開プロフィールの4経路で、kind:0 の name は共通純関数 `normalizeAuthorName` により trim し、trim 後が空なら未名乗りとする。未名乗り時の可視名は専用i18n `author.unnamed` による locale ごとの**「旅人」相当**に統一し、短縮 npub を画面上の名前としては出さない。4経路のプロフィール URL と内部識別は従来どおり npub/pubkey を維持し、**コメント著者名も `/u?npub=…` へのリンク**にする。同名の旅人を支援技術で区別できるよう、投稿カード・投稿詳細・コメントのプロフィールリンクと公開プロフィール見出しの `aria-label` には短縮 npub を補助情報として残す。プロフィールは `fetchProfiles`（一括・`useProfiles` でキャッシュ）。`useProfiles` は **bounded retry**（最大3回・700ms間隔・取りこぼした著者だけ引き直す）で取得し、予算を使い切るまで空 Profile を恒久キャッシュしない（単発取得だと接続直後の取りこぼしを EMPTY で焼いて名前/アイコンが永久に出ない＝#103 デグレ。#93 の `fetchMyProfileResilient` と同じ思想を著者ヘッダ経路にも適用）。拡大モーダルにも同じ著者表示を出し、**複数サイトリンク**（kind:0 拡張 `websites[]`）はモーダル側にアイコン列で載せる（Piece 2・各人が自分のサイトへ誘導する核）。フィードカードにはリンクを出さない。サービス判定は `src/lib/profile/services.ts`（`detectServiceLabel` で URL→サービス名、`serviceIconName` で統一アイコンに対応付け、`toSiteLinks` で表示用に整形）。ブランドロゴの寄せ集めにせず意味カテゴリの統一線アイコンに寄せる（#21・X だけは普及済みで識別性が高いので専用）。各リンクは新規タブ＋`rel="noopener noreferrer"`、`title`/`aria-label` に検出ラベルを入れ識別性を担保。
- **プロフィール編集（#35 Piece3・#104）**: `/me` では **アカウント（ハンドルネーム＋変更/アカウント変更）と `ProfileEditor` を1枚のプロフィールカードに統合**する（`AccountName bare` ＋ `ProfileEditor bare` を MyGrid が1つの glass カードに内包）。ハンドルネーム変更がプロフィール内に収まり、操作ボタンは名前の下段に縦並び（モバイルで窮屈・はみ出さない）。`ProfileEditor` で**アイコン（nostr.build アップロード／URL貼付／削除）・自己紹介・複数サイト（追加/削除/並べ替え）・好きな品種（#141）**を編集。これで hanoba ネイティブ利用者の投稿にも著者ヘッダ（アバター/リンク）が付く。**好きな品種（#141・kind:0 カスタム `favorite_varieties`）**は、投稿タグの `TagPicker`（本文へ挿入）とは別に**選択ロジックをテキスト挿入から分離**した専用 `FavoriteVarietyPicker`（`variety-catalog`/`variety-search` 再利用・カテゴリ→属→品種ドリルダウン＋検索・**葉名だけの複数選択**＝カテゴリ前置しない）で選ぶ。`UserProfile`/`/me` にチップで並べ、タップで discover をその品種で絞る（同好の士の手がかり・#131 人軸）。**kind:0 は replaceable** なので保存は name＋picture＋about＋websites＋favorite_varieties の**全体**を publish する（`client.saveProfile`・部分更新で他項目を消さない。名前だけ変える `saveDisplayName` も付加項目をマージして載せ直す）。初期値はローカル控え（`getProfileExtra`）＋ relay の自分の kind:0（`fetchMyProfileResilient`・bounded retry）で空欄補完し、他デバイス設定も引き継ぐ。relay から非空を掴めたら**ローカル控えにも書き戻す**（表示だけ回復して控えが空のまま残ると、名前変更時の `saveDisplayName` が `websites:[]`/`favorite_varieties:[]` で relay の正本を潰す＝#93/#141 の clobber を防ぐ。`mergeProfileExtra` はローカル非空を優先。`fetchMyProfileResilient` の早期確定/richness は websites＋好きな品種の合計件数で判定）。名前は AccountName 側で設定（未設定なら保存を促す）。**秘密鍵（nsec）バックアップ（#213）**: 展開パネルの**最下部**に nsec の**表示／コピー専用**欄を置く（既定マスク・[表示]トグル・[コピー]）。ブラウザ生成の鍵は控えないと端末変更/データ消去で失われるため、その救済口。値は `exportNsec()` のローカル読み取りのみで、**kind:0（`saveProfile`）の publish payload には絶対に載せない**（表示・コピーするだけ）。`AccountName` の「アカウントを変更」(`importNsec` の貼り付け取り込み)とは別物。
- **投稿詳細（拡大モーダル）**: 写真は**元の比率のまま**見せる（クロップしない・他者著作の改変回避 #61）。複数写真は **←→ボタン／キーボード矢印／タッチスワイプ（左右）**で切り替える（#184・`photoIndex`・端は wrap・純関数 `src/lib/feed/carousel.ts` を全経路で共有。スワイプは水平優位＋しきい値40pxで縦スクロールと競合させない）。**スワイプ中はスワイプ量に応じて写真がぼける（#275）**＝ドラッグの横移動量を `swipeProgress`（[0,1]・既定 maxDx=120px）→`swipeToBlur`（既定 maxBlur=10px）に通し、画像だけを包むラッパに `filter: blur()` で当てる（←→ボタンや `ProgressiveImage` の blur-up リビールには波及させない・両 blur が合成されてもリビールが壊れない）。ドラッグ中は即追従（`transition:none`）、指を離すと 0.25s で 0 に戻り、次画像が中央に来て確定（remount で次画像のぼかしは 0 から）。**単一画像は無効・`prefers-reduced-motion` 時はぼかさない**（縦優位のドラッグも縦スクロール優先でぼかさない）。これらの写像は純関数 `carousel.ts`（`swipeProgress`/`swipeToBlur`）に切り出して市民手帳のページ遷移と共有する。hanoba 自前投稿は 1:1 出力なので正方形に、他クライアントの非正方形はその比率で表示。flex 列の中で `flex-shrink` - **投稿詳細の写真先読み（#544）**: 複数写真の投稿を開いている間、`PostDetail` は現在表示中の写真の前後1枚だけを `Image()` で先読みする。全写真を一斉に読むのではなく、2枚投稿なら相手1枚、3枚以上なら前後2枚に絞り、通信量とメモリを抑えながらスワイプ後の表示待ちを減らす。表示中の写真はモーダル内で即時表示対象なので `loading="eager"` にする。
- **カードの花数・コメント数（#276）**: タイムライン/discover のカード（`PostGrid` 内 `PostCard`）にも**花数（kind:7 集計）・コメント数（リプライ集計）**を出すが、**カードは値が 1 以上のときだけ控えめに添える**（0／未ロードは要素ごと非表示）。一方**投稿詳細（`PostDetail`）は 0 でも表示**する＝**非対称**（カードは「ある時だけ」）。count はカードと `PostDetail` で同じ純関数（`countLikes`/`toComments` 系＝`countLikesByEvent`/`countCommentsByEvent`）を通すので**数え方は一致**し、**0 の出し分けだけが違う**。N+1 を避けるため `PostGrid` がグリッド単位で**1回バッチ取得**し各カードへ配る（catalog/profiles と同じ『まとめ取り→配る』パターン）。**花リアクション（kind:7）とコメント（kind:1）は同じ `#e:ids` 対象で kind だけ違うので、`fetchEngagementCountsBatch` が `{kinds:[7,1], #e:ids}` の1クエリに統合して取得し、取得後に kind で2群へ振り分けて `countLikesByEvent`/`countCommentsByEvent` に渡す（#462＝フィード1ロードの relay 購読を 4→3 に削減。統合クエリは2種相乗りのため limit を2倍にして片方の取りこぼしを防ぐ）。同じバッチ結果から自分の最新花リアクションも `myReactionIds` として持ち、カードCTAと小さい花数アイコンの塗り/文言をリロード直後から揃える（自分が未反応なら花数があっても枠花）。`PostDetail` 内で花やコメントが変わった場合は `PostGrid` に件数・自分の反応状態を戻し、モーダルを閉じた後のタイムライン表示も即時に同期する。フィード本体・著者プロフィール取得は対象 ID／selector が異なり独立必須なので統合しない（4→3 が1ロード内の下限）。**
- **投稿詳細からの花を添える（#529/#537）**: 花のボタン（タップ領域44px）は**押すと花を添え、もう一度押すと取り下げ**のトグル。見た目も連動し、未反応は線画の花（オレンジ）、反応済みは塗りの花（黄色）で出し分ける。未反応状態で押すと標準 NIP-25（kind:7・content `+`）を送信し、反応済み状態で押すとその自分の反応を NIP-09（kind:5）で取り消す。どちらの操作も、読み取りリレーで保存を確認した後に**反応状態（件数＋自分の反応の有無）を relay から再取得**して表示を確定する（ローカルで ±1 演算しない）。投稿を開いた時・投稿を切り替えた時も同じ取得を行い、自分の既存反応があれば反応済み表示から始まる（**反応済みかどうかは localStorage に控えない＝正本は常にリレー上の event**）。送信・取消中はボタンを無効化して連打による二重 publish／二重取消を防ぐ。失敗・保存未確認時は件数・状態を変えず、エラー表示から再試行できる。同一ユーザーの最新反応が既に有効な花リアクションなら再送しない。カード上の花数カウンタは表示専用で、カードCTAは投稿詳細を開いて該当操作へ寄せるだけにする（トグル操作は投稿詳細のみ）。
- **学名表記（#70）**: 学名は属名・種小名をイタリックにするのが正式だが、ランク略号・接続語（`var.`/`subsp.`/`ssp.`/`f.`/`cv.`/`aff.`/`cf.`/交配の `×` 等）は**直立体**にするのが植物学の正しい表記。`src/components/ui/SciName.tsx` が sci 文字列をトークン分割し接続語だけ直立で描画する。PostDetail の植物チップで使う。
- **学名データの丸め方針（#23/#182・`variety-catalog.ts` の `sci`）**: 荒い界隈の表記（Spor/PUP・自分で名乗る品種・属止まり）をどこまで正規化するかの規約。
  1. **書式＝ICNCP**: 属名大文字始まり・種小名小文字（`Pachypodium brevicaule`）。**cultivar は `Genus 'Cultivar'`**＝シングルクォート囲み・各語頭大文字・ただし冠詞/前置詞/接続詞は言語慣習で小文字（`Pierre de Ronsard`・`Perle von Nürnberg`・`Black and Blue`）。**ラテン文字に統一**（漢字 cultivar＝富貴蘭/長生蘭/さつき 等の古典銘も読みを裏取りして romaji 化＝漢字は和名 side で見せる）。
  2. **種が特定できない属通称** → `Genus sp.`（属は当て種は未特定。例 `Sansevieria sp.`・「その他塊根」の通称）。
  3. **状態語・栽培アクション**（実生/発芽/発根/仔株・Spor/PUP・spore 等）は**品種ではない**＝学名を持たせない。これらは `variety-catalog` でなく **`tag-catalog.ts` の世話/記録タグ**に置く（識別子＝品種 と 状態 は別軸＝タグ/札の分離と同じ筋）。
  4. **登録の無い趣味家銘（勝手に名乗る品種）** → 確実な学名が無ければ `Genus '通称ローマ字'` に丸める（白鯨→`Agave titanota 'Hakugei'`）。正式登録名でないものは要検証 follow-up（#182）。
  5. **グループ概念**（コケ/シダ/高山植物/多年草 等＝species でない総称）は `sci` を持たない＝札は**和名のみ**（グレースフル）。
  6. 中身（綴り・読み・trade designation と cultivar の区別）の精度は #23「育てる辞書」として実運用で上げる。書式は上記で統一済み。
- **ヘッダ（全ページ共通・#30）**: 主要ナビ（みんなの植物／自分の植物／Hanōba とは／投稿する）を `SiteHeader.astro` に内蔵。sm 以上はインライン、sm 未満はハンバーガー→ドロップダウン。ページごとの `current` で現在地を強調。`hidden sm:inline` でモバイル時にリンクが消える旧構成は廃止。
- **フッタ（全ページ共通・#532）**: 内部リンクの DOM 順は **市民手帳 → 市政だより → 市勢調査 → 住民投票 → みんなの植物 → あなたの植物 → 投稿する**。市政の実在窓口3件は `civicHub()` と同順、対になる植物一覧2件は隣接させる。デスクトップ左→右／モバイル上→下は同じ DOM 順を `flex-wrap` するだけで成立させ、画面幅別の並べ替えはしない。内部 `nav` はヘッダ等の別ランドマークと区別できる locale 対応の `footer.nav.aria` を持ち、殻の言語 swap でも `aria-label` を追従させる。
- **公開導線（#543）**: フッタは市内案内板なので、追加する公開情報は Nostalgic Counter（来街者）と version に絞る。version は他アプリと同じく SemVer ではなく JST のビルド年月日（`vYYYY-MM-DD`）を表示する。QR / GitHub Sponsors / Amazon アソシエイト道具棚はフッタに詰めない。市民手帳の下は「ハノーバ案内札」（QR）→「園芸師の道具棚」（Amazon アソシエイト、最下部に GitHub Sponsors）の順で分散配置する。QR 画像は `public/hanoba-qr-code.png` を使う。
- **投稿SEO（#542）**: build 時に取得できた Hanoba 投稿だけ `/p/<nevent>` の静的ページを生成し、caption / 画像 / canonical / OGP / Twitter Card / JSON-LD を JS なしで読めるようにする。Nostr 取得失敗時は投稿ページ生成をスキップし、固定ページのみでビルド継続する。フィード上のモーダル復元は従来どおり `?p=<nevent>` を使う。
- **市政だよりのページ順（#533）**: 記事は最古→最新で1から採番し、前＝過去／次＝未来とする。保存位置の無い初回は最終ページ（最新）を開く。共通 `BookPager` の初期解決順は **有効なURL指定 → 有効なlocalStorage保存位置 → `defaultPage`**。市政だよりは `defaultPage="last"`、市民手帳は既定の `"first"` を維持し、不正・削除済みIDは安全に既定端へフォールバックする。
